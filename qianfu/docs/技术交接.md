## 1. 三条铁律（违反会直接坏）

### 1.1 Electron 加载的是 `resources/app.asar`，不是 `resources/xinge/`

改 `main.js` 后**必须重新打包 asar**，否则重启一百次也没用：

```bash
python scripts/deploy_installed.py --restart
```

这个脚本会自动重打 asar 并同步所有源码。**这是本项目最耗时的坑之一**（曾为此浪费数小时）。

### 1.2 QQ 官方机器人一个 appid 只能有一条 WebSocket

本机和服务器同时跑 = 互相踢下线，表现为「机器人时好时坏」。
排查时先确认没有第二个 AstrBot 在跑。

### 1.3 插件里绝不能定义 `__del__`

AstrBot 的 `star_manager.py:2007` 是 `if "__del__" ... elif "terminate"`，
同时定义两者 → **`terminate()` 永远不会被调用** → 后台任务泄漏。
清理逻辑只写在 `terminate()`。

## 2. 数据模型

### 2.1 `items` — 所有抓来的信息条目

```
id, source, uid, board, title, summary, url, category,
published, deadline, extra(JSON), read_at, starred,
created_at, archived_at, pushed_at
UNIQUE(source, uid)
```

- `board` 决定归到前端哪个板块：`course/event/lab/mooc/zhitu/college/shuiyuan/custom`
- `extra` 是各源自己塞的 JSON，**不要假设结构统一**
- `archived_at` 有值 = 在存档区

### 2.2 `events` — 日程

```
id, title, event_date, start_time, end_time, location, note, source, done, created_at
```

`source`：`manual` / `item`（从条目转来的）/ `jwc`（课表）。

### 2.3 `reminder` — 推送队列

```
id, title, body, fire_at, target_type, target_id,
state(pending|sent|skipped|failed), sent_at, retry, created_at, image_url
```

`target_type` 决定文案与去重键：
- `event` / `item` / `mail` / `custom` — 普通提醒
- `digest` — 早报，`target_id=YYYYMMDD` 按天幂等
- `notice` — 公告汇总，同上
- `new_activity` — 新活动，按天幂等
- `alert` — 系统告警

**重要**：`_upsert_reminder` 对 `(target_type, target_id)` 做幂等；
pending 期间内容会**就地刷新**，一旦 `sent` 就冻结。

### 2.4 其它表

`activity_meta`（活动属性缓存）、`alert_state`（告警去重）、`mail_seen`（邮件去重）、
`bot_contacts`（最近联系人）、`sources_state`（抓取健康）、`settings`（配置键值）

## 3. API 契约（94 个路径，这里只列容易踩的）

### 3.1 提醒链路（后端 ↔ 插件）

```
GET  /api/v1/bot/reminders/settings   → {reminder_enabled, advance_event, advance_hw,
                                          advance_hw2, silence_start, silence_end, hourly_cap}
GET  /api/v1/bot/reminders/target     → {umo, bound_at, source(auto|manual)}
GET  /api/v1/bot/reminders/due        → {count, target_bound, enabled,
                                          reminders:[{id,title,body,fire_at,image_url}]}
POST /api/v1/bot/reminders/ack        → {ids:[...]}  或 {ids:[...], mode:"skip"|"failed"}
POST /api/v1/bot/reminders/bind       → {umo, sender_id, nickname}  插件每条私聊都上报
```

**`image_url` 是相对路径**（如 `/api/v1/bot/activities/new.png?hours=24`），
插件用 `SERVER_ROOT + image_url` 拼绝对地址。**别直接 `BASE + image_url`**，会拼出 `/api/v1/api/v1/`。

### 3.2 推送对象是 openid，不是 QQ 号

QQ 官方 API 只给 `user_openid`（`qqofficial_message_event.py:163` 的 `get_user_info` 也只返回
username/avatar/allow_proactive_msg/union_openid）。**永远拿不到 QQ 号**。
UI 里只能让用户从「最近联系人」列表里选。

### 3.3 活动属性

列表接口 `/api/v1/activity/list/home` **不含 custom_properties**，
必须逐条调 `/api/v1/activity/{id}?detail=1`。所以有 `activity_meta` 缓存表 + 后台补全循环。

平台只有三个属性：`是否计入劳动学时` / `劳动学时` / `是否计入新时代社会认知实践讲座课`。
**没有素拓分数**，别去编。

## 4. 登录体系（最容易崩的部分）

### 4.1 两套 cookie 存储

| 文件 | 内容 |
|---|---|
| `~/.xinge/session.json` | jAccount 主会话 + Canvas（SSO 跳转时种下的） |
| `~/.xinge/<site>.json` | 各站自己的 cookie（cnmooc / pe / aihaoke / shuiyuan / impsa） |

**`SessionStore` 只加载 `session.json`**。各站 cookie 要单独 `jaccount.load_site(site)`。
这个不一致导致过「慕课永远检测不到课程」的 bug。

### 4.2 cnmooc 必须走真实浏览器

- 直接访问课程页**不会触发 SSO**，只 302 到登录页
- 必须 Playwright 注入 jAccount cookie → 打开 `/oauth/jacAuth.mooc` → 让 JS 完成跳转
- 登录标志是 **`moocsk`**，不是 `moocvk`（旧的判定是假成功）
- 这个站登录**持久性差**，经常掉，掉了会触发告警

### 4.3 判定「已登录」不要只看 cookie 存在

错的：`bool(jar.get("moocvk"))`
对的：要么用真实 API 探测（Canvas 用 `/api/v1/users/self`），要么用正确的标志位。

## 5. QQ 官方适配器的坑

| 事实 | 证据 |
|---|---|
| 私聊主动推送**无限制** | `qqofficial_platform_adapter.py:559-565` 注释原话 |
| 群主动推送要 scene 缓存 | `adapter:447-470`，重启后群里没来过消息前推送被**静默丢弃**（只 warning） |
| `context.py:714` 说「QQ 官方不支持此法」是**过时注释** | v4.16 起支持私聊、v4.26 起支持群 |
| AstrBot 无出站限流 | 限制全在 QQ 侧，仓库里查不到配额，需实测 |

**因此本项目只做私聊推送**，群聊方案需要额外处理 scene 缓存恢复。

## 6. 关键设计决策（为什么这么做）

| 决策 | 理由 |
|---|---|
| 提醒 = 后端出数据 + 插件负责发 | 后端有数据没 umo；插件有 umo 没数据库 |
| 自然语言建日程走规则解析不走模型 | `/agent/chat` 25–64 秒且有 3–7 次多余调用；`/events/parse` 0.2 秒零误差 |
| 三层优先级：指令 0 / 改设置 -5 / 查询 -8 / 建日程 -10 / 上报 -100 | 高优先级不 `stop_event` 就放行给下一层 |
| 告警用 `alerts.py` 自建 `alert_state` 表 | 避免动 `db.py` 造成多方冲突 |
| 早报过期 2 小时不补发 | 14:00 收到 07:30 的早报是噪音 |
| 公告按 `published` 判新增，不按 `created_at` | 首次全量同步会把 434 条历史全算成新增 |
| 图片分两条发（先文字后图） | 单 chain 图段失败会整条失败，文字也丢 |

## 8. 怎么验证（不要凭感觉说「好了」）

### 8.1 现成验收脚本

```bash
cd qianfu
python scripts/check_reminders.py                    # 提醒系统 9 项
XINGE_TEST_BROWSER_CHANNEL=msedge python scripts/check_gui_redesign.py   # 界面 4 项
```

两个都会**自己清理测试数据**并校验与基线一致。

### 8.2 部署 + 重启

```bash
python scripts/deploy_installed.py --restart
```

⚠️ 会重启整个应用 = 同时重启后端和 AstrBot。
如果只想让插件生效，用 `POST /api/v1/setup/restart`。

### 8.3 真机验证的边界

- **插件侧**：单元测试可以 mock 后端；但「QQ 真的收到了」只能让用户确认
- **推送测试**：往 `reminder` 表插一条 `fire_at=now-1min` 的记录，等 60 秒，
  看日志 `xgine.main:1496 已推送提醒` + `1521 已推送附图`
- **测试时别打扰用户**：临时解绑推送对象，或把 `reminder_hourly_cap` 抬高后立刻恢复

### 8.4 数据安全

测试前备份 `~/.xinge/session.json`，测完**逐字节校验 md5**。
改 `~/.xinge/app.db` 前先 `SELECT` 看清基线计数，测完核对一致。
